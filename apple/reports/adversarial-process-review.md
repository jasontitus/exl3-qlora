It does **not** establish representative output quality or parity with the original model. The first behavioral trial failed its learning objective: `Code?` target NLL increased from 10.0753 to 11.5424, and output changed from the four-token prefix `I'd be happy` to `vvvv`, without EOS. `artifacts/behavior-demo-20261012/report.json` correctly says `needs-investigation`. ## Findings, ordered by consequence

1. **High — selective learning is untested; a constant-output model can pass the behavioral experiment.** Both training examples and the sole untrained wording have the same answer. `behavior_demo.py:62` defines that dataset and `behavior_demo.py:312` allows a pass using only the trained prompt, ablation, reload, and frozen object identities. A model that answers every question with `violet` could satisfy every required check. The first trial's `vvvv` on both wordings already demonstrates the relevance of collapse controls. Add contrasting unrelated prompts and an explicit alternative-answer instruction. Treat any base-pass/adapter-fail control as a regression needing investigation. A transfer success plus control failures is overgeneralization, not quality improvement.

2. **High — whole-model correctness remains outside the evidence.** `RECIPE.md:255` explicitly leaves independent full-model logit parity open. Component tests and teacher-forced loss use the port's own forward path; a consistently wrong forward implementation can train, reload exactly, and fit a toy task. Before claiming fidelity to DeepSeek, compare identical token IDs against a trusted implementation of the same repack/weights: logits, top-k choices, layer outputs, routing, Engram and compressed-attention boundaries. Specify tolerances before seeing results; compare FP32/FP16/BF16 paths separately. Hash equality is appropriate for same-build reload, not cross-engine numeric parity.

3. **High — changing the learning rate after observing results makes the existing untrained wording a development probe.** `behavior_demo.py:185` reuses the earlier baseline and `behavior_demo.py:217` warm starts a selected adapter. That is a valid recovery experiment, but success cannot be presented as one clean prespecified trial or an untouched test. Record the failed 0.003 run, selected step, fresh Adam state, and subsequent 0.0001 run. Report total inherited updates as well as new updates. Reserve a separate final test by task/document family, evaluated only after selection. One paraphrase gives no reliable estimate of generalization; a shared expected answer further weakens it.

4. **Medium — full-model fitting does not isolate the EXL3 expert-adapter contribution.** `behavior_demo.py:116` enables attention adapters across all 40 layers and expert adapters in layer 0. Attention changes alone may explain the answer. Parent inspection reports 80/80 attention B tensors and 96/1152 expert B tensors nonzero at the first trial's step 2; this proves updates in both families, not their causal contribution to output. Report per-family update norms, routed-expert coverage, and a family ablation. Do not call zero gradients in unrouted experts a bug, or nonzero updates proof of useful learning.

5. **Medium — frozen object identity is weaker than frozen value identity.** `behavior_demo.py:124` and `behavior_demo.py:280` compare Python object IDs. In-place mutation can preserve IDs, and `behavior_demo.py:290` checks adapter-off logits on only one prompt/routing pattern. Label the current field exactly as it is, without upgrading it to proof that all base weights are unchanged. Hash frozen resident array contents in bounded chunks and verify sampled read-only bank records before/after; publish which surfaces were sampled. A content fingerprint of selected buffers remains a sample, not a full-bank proof.

6. **Medium — evaluation/generation reports cannot alone reconstruct their inputs.** `src/exl3_mlx/workflow.py:397` stores generated IDs and prompt length but omits prompt IDs, EOS/truncation reason, template hashes, and decoding cap. `workflow.py:439` combines evaluation metrics with model metadata but omits evaluated data hash, selected row IDs, model source commit, adapter tensor hash, and per-example losses. Paths can later refer to different bytes. Add a run manifest with Git commit plus dirty diff hash, lockfile hash, Python/MLX/MLX-LM/OS/device versions, model identity, tokenizer/template hashes, adapter hash, dataset hash and ordered row selection. Save per-example scores, token counts, generations, and stop reasons. The behavioral harness is stronger than the public CLI on several of these fields.

7. **Medium — report reuse can mix executable versions.** `scripts/verify_workflow.py:45` validates model path and fixture hash, then `:60` reuses successful JSON phases. It does not bind them to the trainer source, dependency lock, hardware, adapter artifact hashes, or full base identity. A code change plus `--continue-run` can yield a combined report spanning different implementations. Reject provenance mismatches unless an explicitly labeled historical comparison is intended. In the behavior harness, one-prompt final ablation provides a useful check but does not verify the reused held-out baseline independently.

8. **Medium — the current short run does not validate the supported context/resource envelope.** Existing full-model operational verification trains on four targets (`scripts/verify_workflow.py:105`), while context support extends to 512. The behavioral fixture supplies only 8–9 input positions. Long-run stability, changing expert routing, accumulation, compressed-attention boundaries, near-limit contexts, checkpoint failure recovery, and repeated process startup need staged stress tests. `tests/test_memory.py:5` tests mocked thresholds, not the child-process watchdog exit-and-resume path. Memory reports should distinguish MLX peak, peak RSS, and sampled system headroom. Streaming `loaded_bytes` measures logical reads, not physical SSD traffic; warm OS caches affect throughput.

## Small checks to run after selecting the adapter

The four records in `quality-development-probes.jsonl` are **development and regression probes**, not a benchmark. They are intentionally outside the optimizer and will run only after selecting the adapter. For each, run the base and selected adapter with identical local chat template, prompt token IDs, greedy decoding, and four-token cap. Strip only outer whitespace; require exact case-sensitive expected text and EOS for a pass. Reaching the cap is `truncated`, not an accepted exact answer. Preserve raw text/IDs. A failure under both base and adapter is inconclusive about fine-tuning damage; a base-pass/adapter-fail is a regression. The fresh codeword wording is a transfer observation. Once results influence another training choice, these records are also development data. Report per-case masked target NLL change, exact-match and EOS outcome, base-pass/adapter-fail flags, and unintended `violet` on controls. Four cases support diagnostic observations, not a statistically reliable quality score. Their prompts are new, but their domains and expected answer are deliberately related to the experiment; they are not representative task-disjoint evidence.

**Cheapest family ablation:** use one teacher-forced `Code?` example with full target `violet` plus EOS. Reuse the already recorded all-adapters and all-off logits. Add two forward passes: (a) reload the selected checkpoint and zero only expert `lora_b` tensors, keeping attention unchanged; (b) reload it again and zero only attention `lora_b` tensors, keeping experts unchanged. For each save target NLL, argmax IDs, maximum absolute logit difference from all-on, and first-target probability. Reload after every condition. A measurable all-on versus attention-only difference establishes expert-adapter influence for this prompt. If there is no difference, do not claim expert adapters caused the learned answer; inspect routing/update coverage. Effects are not additive because routing and subsequent nonlinear layers can change. Generate under ablation only if these two inexpensive passes reveal a useful discrepancy.

## Quality gates to implement

| Gate | Evidence and pass condition | What it establishes |
|---|---|---|
| Artifact integrity | Fail closed on bad hashes, wrong tokenizer/template, wrong model/adapter, invalid masks, corrupt optimizer/RNG, and incomplete saves | Reproducible inputs and recoverable state |
| Numerics | Existing dense/finite-difference/VJP tests plus independent complete-model reference traces; predeclared dtype-specific tolerances | Correct forward computation and intended surrogate gradients |
| Causal learning | Target learned to EOS; zero adapter returns base; selected adapter reload reproduces; family norms/ablation recorded; controls do not collapse | This adapter causes the deliberate behavior |
| Task quality | Group-disjoint train/dev/test, duplicate and near-duplicate audit; selected adapter improves a prespecified task metric with paired uncertainty interval, without exceeding a prespecified regression budget | Improvement on the intended task distribution |
| Robustness | Formatting, paraphrase, irrelevant context, conflicting instruction, rare-token, repeated-token and long-input slices; refusal/abstention only where task demands it | Boundaries and failure modes |
| Operations | Cold-process reload and exact resume; bounded multi-step runs at increasing lengths; forced abort/interrupted save/disk-full recovery; peak memory and logical I/O recorded | Reliability in the tested hardware/context envelope |

Useful cheap red-team tests: change only a chat template and expect provenance rejection; feed the same prompt with a different completion across train/test and flag prompt leakage; duplicate paraphrases within a document family and require grouped split; change `loss_start` by one and assert decoded supervision changes; test an EOS-truncated answer; feed a fake `vvvv` report with excellent first-token probability and require overall failure; alter report source commit and prohibit phase reuse; simulate a failed checkpoint write in a child process and prove the last completed checkpoint still loads. Existing checkpoint/mask tests already cover parts of this list; expand them where the new gate adds independent evidence.

For representative task quality, first define the actual intended use and scoring rubric. Run paired base/adapter examples, cluster uncertainty by source family rather than treating correlated tokens as independent samples, and report numerator/denominator and failure slices. If using a model judge, blind and randomize answer order, retain rationales, and calibrate against a small human-labeled subset. Never let a judge substitute for executable correctness checks when the answer is mechanically testable. Tool correctness, successful memorization, and task-quality improvement must remain separate conclusions.
