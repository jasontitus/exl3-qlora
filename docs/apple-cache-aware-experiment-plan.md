# Plan: an adapter that produces better Metal optimizations

Updated 2026-10-15. This is the active decision plan. It supersedes the prior fixed learning-rate/rank/depth sequence, preserved in [the historical plan](apple-cache-aware-experiment-plan-history-2026-10-15.md). The goal is more correct, measurably faster generated kernels from the fine-tuned model than from the same base under the same practical generation allowance. Lower loss, valid patches, and completed training runs are intermediate evidence only.

Code152 achieved 1.115×–1.286×; all four timings are accepted. Old458 remains the provisional candidate for the next distinct task. ## What counts as improvement

For each attempt, record valid response and replay, source/ABI acceptance, compilation, all required numerical cases, and timing only after correctness passes. Keep queue, memory and transport failures separate from model failures. Compare adapters by the number of usable faster kernels on the same completed tasks and budget; show missing coverage and failures. A kernel must also beat the task's supplied baseline implementation to count as an optimization, not merely outperform a worse model sample.

Use the existing qualified timing backend with matching device, workload, precision and cache conditions. Reuse the existing timing policy: five warm-up batches per variant, 30 interleaved paired rounds, 100 dispatches per batch across its 12 declared workloads. Report every target shape and regression, and recheck promising small margins. A future shorter screen must be separately labeled exploratory rather than silently replacing that policy. A repeatable improvement of at least 5% on the declared target workload is a practical initial success target; a smaller or unstable difference is inconclusive, not a win. Never select only the fastest shape after seeing results. Do not turn the report's descriptive median ratios into a certified speedup; use actual backend timing evidence. Baseline/golden controls must show that the task and workload admit a measurable optimization.

One improved task is an encouraging provisional result. Confirm on a second distinct task family before describing a direction as broadly useful. This is a practical screen, not a promise of statistical certainty or unseen-domain generalization. Once repeated task results guide training choices, call those tasks development tests; keep a small unused confirmation task for the selected adapter. Protected16 stays unchanged and is not repeatedly used for selection.

## Correctness and optimization training pilot

The pilot must also teach **profile → hypothesis → change → measured feedback**, not only correctness repairs. The [profile-guided training and evaluation design](apple-profile-guided-kernel-training.md) specifies evidence-bearing chat/tool examples, matched workload variants, no-change decisions, one-decision and feedback evaluations, and profile-use checks. Start with two to four feasible measured optimization pairs alongside correctness cases. This is an explicit extension of the goal; current edit training has not demonstrated it.

Prepare, without launching while the current run is active, an inventory of approximately 16–32 suitable independent changes from the existing collected library. Start with what the sources and runnable tests support; never pad a quota with unverified examples. Focus on alignment/odd tails, accumulator precision and reductions, legal dispatch choices, and workload-specific fusion or memory access. This is curation of existing material; new source collection remains paused.

Each selected example should provide the baseline and task, explicit constraints and representative workload, a concise source-grounded explanation of the bottleneck and change, complete edited code/dispatch, and actual validation evidence where available. Label author-reported measurements and inferred explanations. Do not invent profiling evidence or reward a plausible-sounding rationale without working code. Preserve necessary host/build context rather than pretending every kernel compiles alone.

Use separate training cases to teach unsafe transformation -> observed failure -> corrected implementation, with the accepted implementation as the supervised target. Do not insert held-out evaluation prompts, expected outputs, failed model samples or the exact evaluator oracle into training. A short explanation of alignment, precision, workload assumptions and validation is the reasoning target; long speculative analysis is not. Keep rejection examples and accepted targets clearly distinguished so SFT does not learn the broken solution as its answer.

Use the supported standard SFT path first; no new RL/DPO stack is justified yet. Preserve full items and assistant-target masks. Changing serialization, rationale, loss mode or tokens invalidates assumptions of complete cache reuse. A token-identical suffix-loss experiment remains cheap; a newly formatted correctness pilot pays cold prefix costs. Measure those costs on a few complete representative items and use the smaller useful pilot rather than restarting a 24-hour campaign by default. Freeze its train/development separation and evaluate against the current best adapter before scaling it.
