## Existing mechanism versus required product work

The trainer already has immutable checksummed disk entries and a bounded RAM tier. Keys include complete token IDs, training mode and recompute mode. Disk bindings include full model hashes, implementation, platform/device, quant/activation configuration, chunk size, boundary and state layout. Suffix LoRA rank is not itself a prefix-key field. Rank, alpha and optimizer hyperparameters are absent from the disk binding, but eligibility requires the same earliest attention-or-expert boundary and all existing identities. Any boundary change invalidates this binding. Rank-change reuse is source-supported eligibility, not a completed hardware qualification. Compatibility must be established by actual binding/row checks, not directory names. Training/evaluation caches are intentionally distinct; the current platform binding prevents assuming M5 and Studio entries are interchangeable.

The first useful cross-run speedup does not require a resident worker: fresh workers can reuse the existing verified disk tier while paying model construction and identity scans. Qualify that path first. A resident worker is a later optimization for startup overhead, not a prerequisite that should delay cached trials.

The product now supplies a read-only metadata coverage inspector; it never certifies worker compatibility. First-phase fresh-run reuse is measured for three complete rows. Still needed: a worker compatibility preflight; explicit cache-family inventory; broader cache-family coverage beyond the three-row qualified cross-process resume; a resident multi-trial worker that preserves frozen objects while resetting all learned/optimizer/random/sampler state; trial receipts reporting cold work, warm work, hits/misses/bytes and end-to-end cost. A future multi-boundary producer could capture36/38/39 during one base forward pass, but is not implemented or measured.

Current implementation_identity hashes every package .py/.metal/.html file. Keep experimental workers on the exact pinned runtime-v5 and place new orchestration outside that immutable package; merely installing a helper into a worker package can invalidate its binding. The offline inspector may have a different version, but must distinguish its identity from the requested worker identity. Do not silently broaden compatibility.

A persistent worker must revalidate frozen identity and prevent cross-trial learned-state leakage. Frozen-prefix changes invalidate descendants; suffix changes should not unnecessarily invalidate independently qualified prefix entries. Narrower implementation identities are a future reviewed change, not permission to bypass the current full binding or hash scans. Cache quotas must fit the entire intended working set or report misses/refills explicitly. Do not change sealed runtime-v5 to add these features.
